# Quickstart: Validating `@openimis/fe-ledger`

This guide proves the module works end-to-end within the openIMIS Enterprise Front End shell. It assumes `tasks.md` (generated by `/speckit-tasks`) has been implemented.

## Prerequisites

- `openimis-fe_js` (the host SPA shell) checked out as a sibling directory, with this module registered in its module config (`window.__conf.modules` or the shell's `openimis.json`, pointing `fe-ledger` at `../openimis-fe-ledger_js`).
- `@openimis/fe-core` built (`npm run build` in `openimis-fe-core_js`, since this module depends on it via a `file:` reference).
- A running `openimis-be-ledger_py` backend exposing the GraphQL surface described in `contracts/graphql-operations.md`. **Note (research.md §2)**: as of this plan, the backend module is unimplemented (stub schema files) — until it ships, use a mocked GraphQL endpoint (e.g., a local `graphql-tools` mock server seeded from `contracts/graphql-operations.md`'s response shapes) to validate the frontend independently.
- Two test user accounts: one holding only the module's general ledger reporting right, one holding the finance-administrator right (see `constants.js`'s provisional `RIGHT_LEDGER_REPORTING`/`RIGHT_LEDGER_ADMIN`).

## Setup

```bash
cd openimis-fe-ledger_js
npm install
npm run build        # builds src/ per package.json's "build": "vite build"
```

In the host shell (`openimis-fe_js`):
```bash
npm install ../openimis-fe-ledger_js
npm start
```

## Validation scenarios (one per user story)

Each scenario below is manual (or automatable via a browser-driving test) against the running shell + mock/real backend, logged in as the appropriate test user.

1. **General Ledger Browser (US1)** — Log in as the reporting-only user. Navigate to the ledger browser menu entry. Confirm the initial list is scoped to the current open accounting period (no explicit filter set) and is ordered most-recent-first. Apply a period + party filter combination; confirm only matching entries remain and the filters stay visible/editable. Expand a group row; confirm nested debit/credit lines appear with a balanced subtotal, then collapse it and confirm the subtotal persists. Click through to a source-event reference and confirm it is distinguishable by event type.

2. **Party Sub-Ledger (US2)** — From the same session, search a party using the single unified search box; confirm results span all three party types with type labels. Select a party + period; confirm the statement loads with a signed balance and its legend. Select a party/period combination with no activity; confirm the empty state shows the carried-forward balance instead of an error.

3. **Funder Activity (US3)** — Search and select a funder; confirm aggregated figures render independent of any party filter.

4. **Accounting Periods (US4)** — Log in as the finance-administrator user. Open a new period; confirm it appears with "open" status. Attempt to lock/close a period out of chronological order (e.g., a later period before an earlier one); confirm the backend's specific rejection reason is surfaced verbatim. Log back in as the reporting-only user; confirm lifecycle action controls are absent but period statuses remain visible.

5. **Manual Review Queue (US5)** — As the finance-administrator, open the queue; confirm pending/resolved items show their rejection reason. Resolve a pending item by selecting a correcting entry (confirm the picker only offers entries matching the flagged item's party + period) and entering a note; confirm the item becomes resolved and the original entry has no edit controls anywhere in the UI. As the reporting-only user, confirm the queue is inaccessible.

6. **Period Export (US6)** — As the finance-administrator, trigger an export for an open period, choosing a format; confirm the job status is visible and updates without a manual page reload as it progresses to complete; download the file; confirm the UI labels the numbering "provisional." Repeat against a closed period and confirm the label reads "final."

7. **Deployment Configuration (US7)** — As the finance-administrator, open the configuration screen; confirm operating mode, external system (rendered from the backend's list, not hardcoded), currency code, and retained earnings account are all populated from lookups/dropdowns (no free-text entry). Change the operating mode; confirm the forward-only warning must be acknowledged before save succeeds. As the reporting-only user, confirm this screen is inaccessible.
